# Архитектура и навигация

Начальная карта сверена с исходниками 6 ноября 2026 года. Команды работы — в
[AGENTS.md](../../AGENTS.md), продуктовые сценарии — в [README.md](../../README.md).

## Поток данных

1. `app/app.vue` и `app/layouts/default.vue` задают оболочку Nuxt, навигацию и уведомления.
   Страницы в `app/pages/` используют формы и представления из `app/components/`.
2. `app/composables/useWorkspace.ts` хранит единое состояние через Nuxt `useState`.
   `refresh()` получает представление `Workspace` с ограниченным периодом операций через `GET /api/workspace`; список операций получает отдельные SQL-страницы из `/api/transactions`. [Подробности периодов](import-quality.md). Счётчик запросов
   защищает от замены состояния более старым ответом.
3. `command()` отправляет объект с дискриминатором `op` в `POST /api/command`, затем перечитывает
   пространство. Для редактирования счёта, операции, цели и обязательства composable подставляет
   `expectedRevision`, если форма его не передала. Другие команды с ревизией задают её явно.
   При ответах 404/409 клиент обновляет состояние перед повторной попыткой.
4. `server/api/command.post.ts` проверяет тело через `commandSchema` и переводит ошибки
   ограничений БД в понятные HTTP-ошибки. `server/modules/workspace.ts` объединяет контракты
   и выполняет команды; планирование и долги делегируются соседним модулям.
5. `server/db/index.ts` предоставляет ленивое подключение БД с SQL-миграциями; при штатном запуске
   оно вызывается серверным плагином автоматических копий ещё до первой команды.
   `server/db/schema.ts` описывает таблицы для Drizzle. БД — источник сохраняемого состояния;
   браузерный localStorage не хранит финансовый журнал.

`server/middleware/local-only.ts` выбирает локальную или сессионную границу. В сетевом режиме нормализует API-путь, проверяет Host/Origin, сессию и членство. `executeCommand` повторяет проверку автора внутри SQL-транзакции и записывает его в журнал. Финансовые строки связаны с единственным пространством БД; копии переносят данные без учётных записей и сессий. [Подробности доступа](auth-deployment.md).

## Чтение, запись и экспорт

`readWorkspace()` в `server/modules/workspace.ts` читает связанные таблицы в транзакции
`repeatable read`, `read only`. Разделение действующих и удалённых операций происходит здесь.
`GET /api/backup` использует тот же согласованный снимок и `createBackup()` из `shared/backup.ts`;
`app/composables/useBackup.ts` получает актуальную копию с сервера и скачивает JSON.

Запись сериализуется через `SELECT ... FOR UPDATE` единственной строки `workspace_guard`.
Успешные команды увеличивают её ревизию. Новые операции должны проходить этот путь, чтобы
проверки и связанные изменения оставались атомарными. В частности, запись чека одновременно
создаёт расход и удаляет только отмеченные покупки, а импорт откатывается целиком при ошибке.

Над транзакциями `executeCommand()` держит очередь команд одного процесса. Она охватывает
предварительную копию и запись: параллельная команда не может попасть между снимком перед reset/restore
и заменой данных. После успешного commit вызывается `afterChange()` менеджера копий. Ошибка записи
файла возвращается в статусе копий, а не превращает успешный commit в ошибку финансовой команды.

`server/plugins/automatic-backups.ts` начинает стартовую копию; перед первой записью команда
дожидается той же очереди. При закрытии Nitro плагин ждёт завершения команд и файловых операций.
`server/modules/automatic-backups.ts` получает `readWorkspace` как зависимость, проверяет JSON,
публикует файл через rename и выполняет ротацию. `GET /api/backups` возвращает настройки,
список и ошибку; `GET /api/backups/:name` отдаёт только собственный файл после повторной проверки.
Оба маршрута защищает общий middleware доступа (локальный или сессионный режим). UI использует прежнюю команду `workspace.restore`
с предпросмотром, ревизией и текстовым подтверждением, отдельной логики замены для автокопий нет.

После изменений `syncObligations()` в `server/modules/obligations.ts` согласует долги и планы.
Подтверждение даты плана обязательства вызывает `afterPlanConfirm()`. Изменение связанной
операции проверяется через `checkTransactionEdit()`. Не обходи эти связи отдельной записью в БД.

Перед журналом `finishCommand()` вызывает `syncTransactionDetails()`, `syncCreditCards()` и `syncGoals()` для лимитов, резервов и связанных планов. Журнал добавляется `finishCommand()` из `server/modules/command-history.ts` в той же транзакции, что данные и ревизия. Изменения лимитов фиксируются `syncBudgetHistory()`, контрольные суммы итогов проверяются в той же транзакции. `guardClosedPeriods()` защищает закрытые периоды до изменения данных. Основной `readWorkspace()` не читает журнал; `readWorkspace(true)` включает историю в согласованный снимок для API экспорта и автокопий. Просмотр получает страницы через `GET /api/history`, UI — `app/pages/history.vue`. Подробности — в [command-history.md](command-history.md).

## Где менять поведение

| Задача                    | Основные точки входа                                                                                                                |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Счета и журнал            | `shared/money.ts`, `shared/schemas.ts`, `server/modules/workspace.ts`, страницы accounts/transactions                               |
| CSV-импорт                | `shared/import.ts`, `app/components/ImportForm.vue`, команда `import`                                                               |
| Бюджеты и планы           | `shared/planning*.ts`, `server/modules/planning.ts`, страницы budgets/plans/calendar                                                |
| Прогноз и остатки по дням | `shared/forecast.ts`, страницы forecast/calendar/index, компоненты `ForecastChart.vue` и `ForecastNextIncome.vue`                   |
| Дни выплат                | `shared/workdays.ts`, `shared/planning.ts`, `shared/planning-schemas.ts`                                                            |
| Кредиты и долги           | `shared/obligations.ts`, `server/modules/obligations.ts`, `app/pages/obligations/`, компоненты ObligationForm/ObligationPaymentForm |
| Экспорт и восстановление  | `shared/backup.ts`, API backup, команда `workspace.restore`, `app/pages/backups.vue`                                                |
| Общие формы и диалоги     | `app/components/AppDialog.vue`, предметные компоненты Form                                                                          |
| Тема и оформление         | `nuxt.config.ts`, `app/assets/css/main.css`, `theme.css`, `theme-tokens.css`, предметные CSS-файлы                                  |

При добавлении поля проверь весь путь: SQL-миграция → Drizzle-схема → DTO и Zod → команда
и чтение → импорт/экспорт/преобразование старой копии → форма и отображение → подходящие тесты.
Для финансовых полей дополнительно проверь прогноз, бюджеты и связи обязательств.

## Границы текущей реализации

- `/recurring` перенаправляется на `/plans` через `routeRules` в `nuxt.config.ts`.
- Клиент по-прежнему получает пространство целиком. Загрузка по периодам — будущая работа.
- Категории используют ID и внешние ключи; отображаемые имена поддерживаются совместимым SQL-триггером.
- `localDate()` использует часовой пояс пространства; настройка загружается из БД и применяется на клиенте.
- Автоматические копии работают в одном процессе приложения; счётчик интервала хранится в памяти,
  а файлы и ротация — на серверном диске. Несколько серверов с общей папкой копий пока не поддерживаются.
- Авторизация, семейные пространства,
  PWA, синхронизация и внешние уведомления пока относятся к roadmap.

Подробности финансовых связей — в [domain.md](domain.md), хранения — в
[development.md](development.md). Будущие этапы и причины отложенных изменений — в
[CONCEPT_AND_ROADMAP.md](../../CONCEPT_AND_ROADMAP.md).
