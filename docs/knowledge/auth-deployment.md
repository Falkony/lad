# Личный сервер: доступ, сессии и перенос

Итерация 9: миграция 16, финансовые копии версии 11 с чтением версий 1–10.
Текущий объём — личное пространство одного владельца. Семейный режим отложен пользователем
до проверки личной синхронизации.

## Граница доступа

Без `LAD_AUTH_ENABLED=1` сохраняется локальный режим: loopback, Host и same-origin.
`npm run dev` и `preview` остаются локальными. `npm start` запускает собранный сервер;
сетевой режим требует явного включения авторизации и `LAD_PUBLIC_ORIGIN` с HTTPS.
Исключение HTTP предназначено для тестирования: `LAD_AUTH_ALLOW_HTTP=1` допускает только
loopback и сохраняет локальную привязку процесса.

`server/middleware/local-only.ts` теперь выбирает локальную либо сессионную границу.
В сетевом режиме проверяются точные Host/Origin; изменения требуют Origin. Заголовки
переадресации не заменяют настроенный адрес. Нормализация API-пути выполняется до проверки,
включая кодированные символы и регистр. Запросы браузера с чужого сайта отклоняются;
ответы API имеют no-store, nosniff и same-origin resource policy.

Пароли хэшируются встроенным scrypt: N=32768, r=8, p=3, случайная соль 16 байт,
выход 64 байта, сравнение timingSafeEqual. Этот набор выбран из
[вариантов OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#scrypt)
с учётом памяти личного сервера; реализация использует [Node crypto](https://nodejs.org/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback).
Минимум нового пароля — 12 символов. Проверка неизвестного имени выполняет тот же расчёт.
Лимиты попыток: 10 на адрес подключения и 60 суммарно за 15 минут; за прокси адрес подключения
общий, заголовкам X-Forwarded-For приложение не доверяет.

Сессия — случайный 256-битный токен на семь дней, в БД только SHA-256. Cookie HTTPS имеет
имя `__Host-lad_session`, Secure, HttpOnly, SameSite=Strict и Path=/; локальный тестовый HTTP
использует другое имя. Пользователь видит устройства и может завершить сессию. Смена пароля
отзывает прежние сессии и создаёт новую для текущего устройства. Максимум 20 активных сессий.
При выходе очищается клиентское состояние. Если сеть пропала, локальная отметка выхода
не допускает автоматического возвращения в прежнюю сессию; отзыв повторяется при подключении.

## Пользователь и данные

`auth_workspaces` содержит одно пространство на БД с владельцем; `auth_memberships` задаёт
доступ, `auth_sessions` — сессии. Публичной регистрации нет. Владелец создаётся только из
настройки сервера при первом запуске без существующего владельца. Повторный запуск не
переписывает его пароль значением bootstrap-переменной.

Каждая финансовая таблица связана с пространством через workspace_id, внешний ключ и
проверку единственного пространства. Клиент не выбирает пространство для чтения/записи.
HTTP проверяет сессию, а `executeCommand` повторяет проверку сессии, членства и роли внутри
транзакции после ожидания очереди. Read-only роль не пишет; reset/restore доступны владельцу.
Семейные приглашения и интерфейс дополнительных пользователей пока не включены.

Журнал фиксирует ID и имя автора из проверенного сервером контекста. Пароли и токены в него
не попадают. Финансовый экспорт исключает таблицы доступа и физические workspace_id;
копия переносит деньги и историю, а текущие владелец/сессии принимающего сервера сохраняются.
Историческое имя автора остаётся частью журнала. Reset также не удаляет владельца.

## Подготовленное размещение

Модель: один личный сервер Docker Compose, PostgreSQL 17, приложение Node 26 и Caddy.
PostgreSQL и приложение не публикуют порты на хост; извне доступны 80/443 Caddy.
Приложение работает не от root, с read-only корнем, отдельным томом копий и временным /tmp.
База получает отдельную прикладную роль без superuser/createdb/createrole.
В Caddy заданы HTTPS, заголовки и лимиты тела 4 КБ для паролей, 25 МБ для остальных запросов;
см. [request_body](https://caddyserver.com/docs/caddyfile/directives/request_body) и
[reverse_proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy).

1. Подготовить сервер с Docker Compose и собственное DNS-имя, направленное на него.
2. Скопировать `.env.server.example` в `.env.server`; файл исключён из Git и Docker build context.
3. Выполнить `npm run auth:hash` и поместить результат в LAD_OWNER_PASSWORD_HASH в одинарных
   кавычках. Пароль вводится без эха; в shell-команду его передавать не нужно.
4. Задать два разных случайных hex-пароля PostgreSQL, имя владельца и LAD_HOSTNAME.
   Пример генератора пароля: `node -e "console.log(require('node:crypto').randomBytes(24).toString('hex'))"`.
   Hex исключает необходимость URL-кодирования пароля в DATABASE_URL.
5. Из корня проекта:

```sh
docker compose --env-file .env.server -f deploy/compose.server.yaml config --quiet
docker compose --env-file .env.server -f deploy/compose.server.yaml up -d --build --wait
```

Войти по HTTPS-адресу и через «Резервные копии» восстановить JSON из локального приложения.
Перенос каталога `.data/lad` в PostgreSQL не выполняется; используется проверяемый JSON.
Не удалять тома при обычном обновлении. Переменные bootstrap и PostgreSQL-пароли не меняют
уже созданные учётные записи простым редактированием env; пароль владельца меняется в UI.

## Копии и восстановление доступа

Сервер использует прежний менеджер автоматических JSON-копий: запуск, каждые N изменений,
перед reset/restore. В серверном compose — отдельный том `/backups`, 30 последних файлов
по умолчанию, доступ файлов у UID 1000. Скачать копии можно после входа. Для защиты от потери
самого сервера нужен отдельный носитель/хранилище: локальный том не переносится на другой хост сам.

Восстановление на новый сервер: поднять пустую БД, настроить владельца, войти и загрузить JSON.
Финансовые ID и связи сохраняются; пространство и учётные данные относятся к новому серверу.

Для забытого пароля администратор сначала создаёт новый хэш и задаёт его в env, затем:

```sh
docker compose --env-file .env.server -f deploy/compose.server.yaml stop app
docker compose --env-file .env.server -f deploy/compose.server.yaml run --rm --no-deps app node scripts/reset-owner.mjs --confirm-reset
docker compose --env-file .env.server -f deploy/compose.server.yaml up -d --wait
```

Скрипт меняет только пароль владельца и отзывает сессии. Для локальной PGlite требуется
остановленное приложение и явно заданный LAD_DATA_DIR. Скрипт отказывается открывать БД с
существующим lock-файлом. После аварийной остановки сначала проверить отсутствие процесса
и только затем удалить старый файл блокировки; сам каталог БД не удалять.

## Проверки и остаток аудита

Локально выполнены 197 тестов, типы, production build и `npm run test:production`:
последняя команда запускает собранный API с отдельной временной БД, проверяет вход,
закрытый API, создание факта, автокопии и атомарное восстановление с сохранением сессии.
Она не открывает браузер и не использует пользовательскую БД. PostgreSQL-тест отдельно
требует LAD_TEST_DATABASE_URL с именем БД lad_test_*; без него пропускается.

В CI добавлены PostgreSQL restore, сборка Docker, проверка Caddy, запуск backend и smoke
в контейнере. На текущем компьютере Docker отсутствует; выполнение этих задач CI, выдача
сертификата на реальном домене и проверка телефона требуют подтверждения фактическим запуском.
Браузерная визуальная проверка ранее отклонена и не обходилась.

Аудит 6 ноября 2026 после обновления glob/minimatch/esbuild: moderate/high/critical — 0,
low — 7 зависимых пакетов одной цепочки deepmerge. Для
[GHSA-gcqx-w48m-w2h4](https://github.com/advisories/GHSA-gcqx-w48m-w2h4) опубликованного
исправления нет. Использование — цепочка сборки; пакет deepmerge отсутствует в проверенном
traced runtime `.output/server/node_modules`. Полный node_modules сборки в runtime-образ не копируется.
Сборка и тесты проверены после overrides; install scripts esbuild/vue-demi разрешены только
для закреплённых версий через allowScripts. Аудит перед выпуском повторять.
