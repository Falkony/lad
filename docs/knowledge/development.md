# Окружение, БД и проверки

Сверено с конфигурацией и исходниками 6 ноября 2026 года.
Основные npm-команды собраны в [AGENTS.md](../../AGENTS.md).

## Локальная работа

`npm ci` устанавливает зависимости по `package-lock.json` и запускает `nuxt prepare`.
`npm run dev` привязывает сервер к `127.0.0.1`; обычный адрес — порт 3000.
После `npm run build` команда `npm run preview` запускает `.output/server/index.mjs`
через `scripts/preview.mjs`, принудительно оставляя `NITRO_HOST=127.0.0.1`.
Порт preview можно изменить через `NITRO_PORT`.

Для задачи только с документацией не нужны запуск приложения и подключение пользовательской БД.
Зависимости и код сгенерированных каталогов не являются источником знаний о проекте.

| Переменная          | Поведение                                                                            |
| ------------------- | ------------------------------------------------------------------------------------ |
| `DATABASE_URL`      | При наличии выбирает PostgreSQL; иначе используется PGlite                           |
| `LAD_DATA_DIR`      | Папка PGlite, по умолчанию `.data/lad`, разрешается относительно cwd                 |
| `LAD_BACKUP_DIR`    | Папка JSON-автокопий; по умолчанию `backups` рядом с папкой PGlite (`.data/backups`) |
| `LAD_BACKUP_EVERY`  | Интервал успешных изменений между копиями, целое число от 1, по умолчанию 10         |
| `LAD_BACKUP_KEEP`   | Число сохраняемых автокопий, целое число от 2, по умолчанию 20                       |
| `POSTGRES_PASSWORD` | Обязательный пароль для сервиса db в `compose.yaml`                                  |
| `NITRO_HOST`        | Упомянут в `.env.example`; штатные dev/preview сохраняют loopback                    |
| `NITRO_PORT`        | Порт production preview, по умолчанию 3000                                           |

Пример настроек находится в [.env.example](../../.env.example).
Для PostgreSQL сначала настрой `DATABASE_URL` и пароль, затем при необходимости выполни
`docker compose up -d db`. Compose использует PostgreSQL 17, локальный порт 5432 и volume
`lad-postgres`. Подключение PostgreSQL создаётся через postgres-js с пулом до 5 соединений.
Смена подключения не переносит данные: для переноса используй экспорт и восстановление копии.

## PGlite и сохранность данных

PGlite хранит данные на диске, а не в браузере. `server/db/index.ts` создаёт рядом с папкой
БД PID-файл `<LAD_DATA_DIR>.lock` и отклоняет второй живой процесс с той же папкой.
Не запускай dev и preview одновременно на одной БД и не удаляй блокировку работающего процесса.
Для параллельного эксперимента задай другую папку, например в PowerShell:

```powershell
$env:LAD_DATA_DIR = '.data/lad-sandbox'
npm run dev
```

Если в среде задан `DATABASE_URL`, он имеет приоритет над `LAD_DATA_DIR`.
Не выполняй сброс, демо-заполнение и тестовые команды на пользовательской БД.
Ручная файловая копия `.data/lad` делается после остановки приложения.

Каталог, часовой пояс, CI и тесты миграции 11 описаны в [foundation.md](foundation.md).

## Миграции

`getDb()` при первом обращении выполняет `migration` из `server/db/migration.ts`.
Это SQL-транзакция: начальная схема плюс версионированные обновления, учтённые в `lad_migrations`.
SQL общий для PGlite и PostgreSQL. Текущее состояние — версии 1–15:

| Версия | Изменение / файл                                                                         |
| ------ | ---------------------------------------------------------------------------------------- |
| 1–3    | Начальная схема, нулевой остаток долга, архив/корзина, импорт и ревизии — `migration.ts` |
| 4      | Исправление исходного счёта импорта и индекса — `repair-import-origin.ts`                |
| 5      | Бюджеты, расписания, версии, отметки — `planning-migration.ts`                           |
| 6      | Единые планы доходов/расходов и перенос событий — `unified-plan-migration.ts`            |
| 7      | Участие счетов в прогнозе — `forecast-migration.ts`                                      |
| 8      | Несколько дней выплат и перенос с выходных — `pay-days-migration.ts`                     |
| 9      | Начальный остаток долга, история погашений и график-план — `obligation-migration.ts`     |
| 11     | Категории с ID и пояс — `foundation-migration.ts`                                        |
| 12     | Кредитные карты и график банка — `credit-migration.ts`                                   |
| 13     | Потребности и резервы — `goals-migration.ts`                                             |
| 15     | История лимитов, сверки и закрытие месяца — `periods-migration.ts`                       |
| 14     | Ключи, правила и пакеты импорта, разделение и возвраты — `import-quality-migration.ts`   |
| 10     | Транзакционный журнал команд — `command-history-migration.ts`                            |

Файлы таблицы находятся в `server/db/`. Новое изменение добавляй новой версией с проверкой
применения; одного исправления начального `CREATE TABLE IF NOT EXISTS` недостаточно для старой БД.
Уже применённую ошибочную миграцию исправляй следующей миграцией.
Синхронно обновляй `server/db/schema.ts`, DTO, Zod и преобразование резервной копии.

`drizzle.config.ts` используется для инструментов работы со схемой; проект не применяет
миграции через drizzle-kit. Проверяй сохранность старых записей и повторное применение SQL.
`tests/schema-drift.test.ts` сравнивает таблицы, столбцы и обязательность значений Drizzle со
схемой, реально созданной SQL. Он не заменяет проверки индексов, ограничений и сохранности данных.

## Резервные копии

Миграция 10 добавляет `command_history` с ревизией, временем, операцией, JSON-данными и результатом.
Начальное состояние журнала пустое, старые финансовые записи и ревизия сохраняются.

`shared/backup.ts` экспортирует версию 10 с журналом, назначениями и импортом, преобразует версии 1–9 и ранние копии версии 4
с отсутствующими позднее добавленными полями. Формат проверяет уникальность ID и связи,
включает архив, корзину, бюджеты, планы, версии, решения по датам и историю долга.

Восстановление — полная атомарная замена, без объединения с текущими записями.
UI ограничивает файл 25 МБ, показывает предпросмотр; команда требует `expectedRevision`
и точный текст `ВОССТАНОВИТЬ`. Изменение пространства после предпросмотра отклоняет замену.
Ревизия пространства не экспортируется отдельным полем. После восстановления новая ревизия
выбирается выше прежней локальной ревизии и максимальной ревизии импортированной истории.
Не удаляй поддержку старых файлов при добавлении новых полей.

### Автоматические копии и ротация

Менеджер — `server/modules/automatic-backups.ts`; Nitro-плагин запуска —
`server/plugins/automatic-backups.ts`. Для самих автокопий миграция не требовалась; добавленный журнал использует миграцию 10 и JSON-формат версии 5.
Копия создаётся при запуске, после `LAD_BACKUP_EVERY` успешных команд (включая demo/restore/reset)
и дополнительно перед reset/restore. Счётчик в памяти обнуляется после успешной записи и при запуске.
При reset/restore отсчёт начинается от предварительного снимка; при интервале 1 создаётся и снимок
после изменения. Минимальная ротация в 2 файла сохраняет предыдущие данные рядом с ним.

`executeCommand()` сериализует весь цикл команды, включая предварительную копию, затем сохраняет
существующую блокировку `workspace_guard` внутри транзакции. Это исключает потерю параллельного
изменения между предварительным снимком и очисткой в одном процессе приложения.
После ошибки самой команды счётчик не увеличивается. После ошибки файловой записи команда,
уже завершившая commit, остаётся успешной; ошибка сохраняется в статусе и повторная попытка
выполняется после следующего успешного изменения. Reset/restore без предварительной копии возвращает
503 до изменения данных. При остановке Nitro ожидается завершение команд и очереди копирования.

Порядок записи:

1. Согласованный `readWorkspace()` → `createBackup()` → полная проверка `backupSchema`.
2. Проверка предела 25 МБ; запись собственного уникального `.json.tmp` с `wx`, режимом 0600
   (на системах с Unix-правами) и `sync()` дескриптора.
3. Перечитывание файла, сравнение байтов и повторная проверка схемы.
4. Переименование в `lad-auto-<timestamp>-<uuid>.json` в той же папке.
5. Удаление самых старых собственных JSON-файлов сверх лимита. Имена имеют возрастающую
   временную метку для однозначного порядка даже при совпадении миллисекунд; фактическая дата
   экспорта также записана внутри JSON в `exportedAt`.

Не удаляй старые файлы до публикации новой копии. Ручные JSON, каталоги, симлинки и временные файлы
не участвуют в списке и ротации. Незавершённый `.tmp` после аварийной остановки не считается копией.
Текущая реализация рассчитана на один процесс приложения и собственную папку для каждой БД.
Автоматический backup — логический JSON-снимок, не копирование открытых файлов PGlite.

`GET /api/backups` отдаёт `AutomaticBackupStatus` из `shared/automatic-backups.ts`.
`GET /api/backups/:name` принимает только строгое имя существующего собственного файла,
ограничивает размер и валидирует его перед выдачей. Произвольные пути и повреждённые файлы
не отдаются. UI показывает дату, настройки, ошибку и список со скачиванием/подготовкой восстановления.
И локальный файл, и выбранная автокопия проходят `backupSchema`; UI принимает версии 1–10; версии до 5 получают пустую историю, до 6 — каталог из сохранённых имён.

`tests/automatic-backups.test.ts` проверяет запуск, порог только успешных изменений, конкурирующие
команды, ротацию без удаления ручных файлов, отказ файловой системы с последующим восстановлением,
сохранение предыдущей копии при ошибке валидации и защиту перед очисткой. Отдельный сценарий
читает реальные байты автоматического файла и восстанавливает их командой в **другую пустую PGlite**;
сравнивает все разделы и связи, включая архив, корзину, импортное происхождение, планы и погашения.
Пользовательская `.data/lad` в проверках не используется. Проверка схемы при каждом сохранении
не означает пробного восстановления в БД при каждом запуске — реальное восстановление проверяет тест.

В файловой песочнице Windows системный TEMP может разрешать создание файла, но запрещать rename.
В такой среде направляй TEMP/TMP тестового процесса в собственную игнорируемую папку
`artifacts/test-tmp` внутри репозитория. Атомарную публикацию копии не заменяй неатомарной записью
для обхода ограничения среды.

Журнал и правила замены его истории подробно описаны в [command-history.md](command-history.md). Проверки транзакционного журнала и миграции 10 — `tests/command-history.test.ts`.

## Карта тестов

Vitest настроен в `vitest.config.ts` на `tests/**/*.test.ts`; таймауты тестов и хуков — 30 секунд.
Интеграционные сценарии используют временные папки или in-memory PGlite и снимают `DATABASE_URL`.
Эти тесты проверяют PGlite; они не подтверждают отдельный запуск внешнего PostgreSQL.

| Область                                                       | Файлы в `tests/`                                                                                             |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Суммы, CSV                                                    | `money.test.ts`, `import.test.ts`                                                                            |
| Журнал, атомарность, ревизии, восстановление                  | `workspace.test.ts`, `iteration-two.test.ts`, `review-fixes.test.ts`                                         |
| Локальная граница API                                         | `local-api.test.ts`                                                                                          |
| Миграции и соответствие схем                                  | `migration.test.ts`, `schema-drift.test.ts`, `import-origin-migration.test.ts`, `planning-migration.test.ts` |
| Бюджеты, версии планов, подтверждения                         | `planning.test.ts`, `planning-commands.test.ts`, `unified-plans.test.ts`                                     |
| Прогноз и участие счетов                                      | `forecast.test.ts`, `forecast-accounts.test.ts`                                                              |
| Производственный календарь и дни выплат                       | `pay-days.test.ts`                                                                                           |
| Долги, графики, погашение и миграция 9                        | `obligations.test.ts`                                                                                        |
| Автокопии, ротация, ошибки диска и восстановление в другую БД | `automatic-backups.test.ts`                                                                                  |

Для изменения расчётов добавляй тест на конкретный инвариант или ошибку. Для изменений БД
проверяй обновление старого состояния и обратную совместимость копий. UI-изменения дополнительно
проверяй вручную в затронутом сценарии, на узком экране и в обеих темах.

Prettier использует `.prettierrc.json`: два пробела по умолчанию, без точек с запятой,
одинарные кавычки, trailing comma, ширина 100. `npm run format:check` проверяет весь проект;
для документации можно вызвать `npm exec --offline -- prettier --check AGENTS.md docs/knowledge/*.md README.md`.
