# Периоды, проверяемый импорт и качество учёта

Итерация 7: миграция 14, JSON-копии версии 9 с чтением версий 1–8.

## Загрузка операций

`GET /api/transactions` выполняет фильтрацию, SQL-пагинацию и агрегаты в согласованной
read-only транзакции. По умолчанию 20 строк, максимум 100; порядок дата/время/ID.
Фильтры: месяц либо from/to, вид, категория (включая части), оба счёта перевода, поиск,
корзина и ID связанной операции. Итоги относятся ко всему фильтру, а не к странице.
Категория отбирает целые операции, суммы частей раскрываются в бюджете.

Обычный `/api/workspace` читает операции начиная с `from` (по умолчанию последние 100 дней).
До начала периода SQL агрегирует денежные движения по счетам и прибавляет их к начальному
остатку клиентского представления. Исходный редактируемый остаток остаётся в
`originalOpeningBalance`. `setPeriod()` расширяет окно до выбранного месяца с запасом для
календаря. Конец фактической истории — текущие данные; при выборе давнего месяца загружается
период от него до текущей даты. Дальнейшее ограничение такого длинного окна — отдельная оптимизация.
Ссылки на операции, подтверждающие даты в окне, и ID действующих погашений передаются отдельно:
старые платежи не становятся повторно открытыми. Экспорт и команды используют полную модель
с исходными остатками; клиентское представление не является резервной копией.

## Проверка и применение CSV

`shared/import.ts` сохраняет прежние ключи: банковский ID либо нормализованная строка
с номером повторения. `POST /api/import/preview` применяет правила и предлагает точные
совпадения ручных строк (дата, сумма, вид, счёт), стороны своих переводов и даты планов
с такой же суммой в пределах трёх дней. Это предложения: по умолчанию создаётся новая запись,
спорные строки нужно выбрать вручную или пропустить. Сопоставление проверяется повторно
в транзакции, UI отправляет ревизию предпросмотра. Изменившееся пространство требует нового просмотра.

Правила — подстрока описания без учёта регистра, с необязательными счётом и видом операции.
Меньший приоритет применяется первым; регулярные выражения не исполняются. Категория берётся
из активного каталога. Сопоставленная ручная запись сохраняет свои поля; импорт добавляет
банковский ключ. Шаблоны колонок хранятся на сервере, а не только на устройстве.

`import_keys` сохраняет исходные счёт/ключ независимо от правок, разделения и удаления
операции. Один перевод может иметь ключи обеих банковских сторон. При переносе записи на
другой счёт повторный импорт не создаёт дубль. Старые копии получают ключи из importKey /
importAccountId. Без банковского ID пересекающиеся одинаковые строки остаются неоднозначными.

Пакет хранит имя файла, ревизию, отчёт и снимки затронутых операций. Исходный CSV не хранится.
История загружается страницами в `/imports`; обычное пространство получает только последние
30 отчётов без снимков и полного списка ключей. Полные данные входят в экспорт.
Предпросмотр отмены показывает последствия и блокирующие причины. Неизменённые созданные
операции перемещаются в корзину, ключи пакета освобождаются; прежние сопоставленные записи
сохраняются. Изменения строк, планы, погашения, покупки, возвраты и ключи других пакетов
блокируют отмену. Автоматическое удаление зависимых финансовых записей не выполняется.

## Разделение и возвраты

Один расход хранит массив `splits` с ID категорий и целыми копейками; сумма частей равна
операции, категории уникальны. Баланс меняется один раз. Переименование и объединение
категорий обновляют части; при объединении их суммы складываются. Массовая категоризация
заменяет разделение одной категорией; категории возврата определяются покупкой.

Доход с `refundOf` относится к исходному расходу. Возврат уменьшает расходы в месяце
возврата и исключается из доходов, сохраняя реальное поступление на счёт. Дата не раньше
покупки, сумма активных возвратов не больше её стоимости; удаление покупки с активными
возвратами отклоняется. При разделённой покупке возвраты распределяются по оставшимся
суммам категорий, остаток копеек распределяется в устойчивом порядке. Несколько маленьких
возвратов не создают отрицательных частей и возвращают полную исходную сумму.
Возвраты целей используют ту же связь. `syncTransactionDetails()` выполняется до остальных
инвариантов и журнала в общей транзакции; неверные суммы откатывают всю команду.

Визуальная проверка не проведена из-за ранее отклонённого доступа браузера.
